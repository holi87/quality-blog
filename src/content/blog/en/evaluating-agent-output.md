When a team starts using AI agents seriously, a new task shows up that didn't exist before: **verifying what the agent produced**. For a tester that's good news, because it's largely the same thing we do every day anyway — critical review of output — just with a new kind of source and new failure patterns.

In this post I'll unpack how to approach agent-output evaluation systematically. For example: a test scenario generated by an agent, a changelog analysis, a proposed release readiness checklist, generated API docs. The mechanism is similar; only the specifics change.

The goal isn't to "catch AI lying." The goal is to have a stable set of questions you ask every output before you let it move forward.

## Five dimensions of evaluation

Five dimensions. Each answers a different question and each catches a different kind of problem.

### 1. Completeness

Question: **does the output cover everything it was supposed to cover?**

An agent asked for "test scenarios for the new coupon feature" can easily produce 8 great scenarios and 4 silent omissions. You won't see the omissions by looking at what it wrote — you'll see them by comparing with what should have been there.

Practical approach: before you call the agent, write down the **list of areas that should appear** in the output. When the result arrives, confront it line-by-line. If you're asking for scenarios, your list should include: happy path, main negative scenarios, edge cases, validation errors, interactions with other modules, offline behaviour, non-functional requirements.

Typical symptom: the agent has a bias toward **positive paths**. It will almost always skip a class of errors unless you explicitly ask for them.

### 2. Factual correctness

Question: **is what the agent claims actually true?**

The most obvious dimension and the easiest to defend, but in practice the most ignored during review, because the output looks credible.

Verification approaches that work:

- **Cross-check with code**. If the agent describes a function's behaviour, look in the code. Three random claims are enough to trust the rest.
- **Cross-check with the spec**. If the agent refers to requirements, check whether it cites real fragments. Good tools cite. If they don't cite — suspect.
- **Standalone-claim test**. Take one claim from the output and ask "how do you know?". If the agent can't point to a source or reconstruct the reasoning, that's a signal.

The most dangerous factual-error variant is **precise but false**. "Endpoint `/api/v2/discounts` accepts a `max_uses` field" — sounds specific, often invented.

### 3. Domain alignment

Question: **does the output stick to the conventions of your project, team, product?**

This is the dimension agents massively neglect, because they don't know them. It's not in their training — unless you explicitly hand it over via `AGENTS.md`, docs, examples.

Specifics I check:

- **Naming** — is the scenario named per your convention (`should ... when ...` vs descriptive sentences).
- **Selectors / identifiers** — are `data-testid` used, not CSS classes, if that's your rule.
- **Terminology** — does it use yours or fall back to generic ("user" vs "customer" vs "merchant", if that distinction matters).
- **Structural conventions** — where the file lives, what header it has, which imports.

Without this dimension, the output can be technically correct but not fit the team. It comes back in review even if everything else is fine.

### 4. Traceability to sources

Question: **can you verify where each claim came from?**

A critical dimension for anything the agent generates from evidence (log analyses, bug history, documentation). Without traceability, you as reviewer have no chance of verifying correctness.

Good output has:

- **citations pointing to a specific ticket / log / file**,
- **links or identifiers** a human can click,
- **date / version** of the source, where relevant.

Bad output has:

- claims like "our logs show that…" without pointing to a specific log,
- "the docs say…" without a reference,
- "in recent commits…" without hashes.

If this sounds strict, that's because it is. Without traceability, you can't tell an evidence-based conclusion from a hallucination, and the cost of that difference in QA is high.

### 5. The "pretty nonsense" risk

Question: **is the fact that the output looks great the only reason you're accepting it?**

This is a meta-dimension. It's about reviewer self-awareness. Well-phrased, neatly structured, stylistically consistent text creates an illusion of correctness. After two hours of review, a tester starts trusting form.

Antidote: pick random fragments and check them very aggressively. If a random fragment passes three deep checks, the rest probably will too. If it breaks — the rest needs deeper verification, not shallow acceptance.

Second mechanism: count how many times in your review you said "looks reasonable." If more than twice for a single output — you're reviewing form, not content.

## Review checklist — practical version

Putting it together, a structured checklist I keep as a template:

**Completeness**
- [ ] Output covers all areas from my pre-written list.
- [ ] No obvious missing scenario classes / threads.
- [ ] Scope matches what I asked for.

**Correctness**
- [ ] Random check of 3 claims against code/spec.
- [ ] No detailed-but-unverifiable facts (endpoint names, fields, constants).
- [ ] Numeric values, if any, have a source.

**Domain alignment**
- [ ] Naming matches conventions.
- [ ] Selectors / types / file structure match the repo.
- [ ] Product terminology is consistent.

**Traceability**
- [ ] Every evidence-based claim has a citation.
- [ ] Cited sources are openable and current.
- [ ] No "our data shows…" without a link.

**Pretty nonsense**
- [ ] Form didn't mask missing content — I did a random sample.
- [ ] I didn't accept anything "because it looks reasonable."
- [ ] I hand-verified the three most precise claims.

Fifteen points. Fifteen minutes if you do it regularly.

## When to reject without discussion

There are situations where I don't waste time on a careful review and just send the output back. I treat them as red flags:

**1. No sources for evidence claims.**
Output like "last month we had flaky tests in area X" without naming which ones. Reject.

**2. Invented API / field / file names.**
One such instance is enough to question the whole output. Reject and regenerate with an explicit citation requirement.

**3. Internal contradictions.**
"The test should verify the coupon is single-use" — and three lines later "…after multiple uses the coupon still works." Both lines can be real, but the agent didn't notice the conflict. Reject.

**4. Non-compliance with explicit instructions.**
You asked for BDD-style scenarios and got an imperative list of steps. Don't fix it manually — send it back. Otherwise the agent won't learn it can't wriggle out of instructions.

**5. Output too generic.**
"The system should be reliable" — when you asked for concrete scenarios. Reject with a request for specificity.

In each case the cost of sending it back (30 seconds of prompting) is lower than the cost of manual fixing (30 minutes). Sending it back is pro-quality.

## Scaling review — what's next

In bigger teams, reviewing agents yourself stops scaling. Two practices that work:

**AI reviewing AI (as a pre-filter).** A second model checks the output against the checklist above and flags what needs human attention. It doesn't eliminate human review — it eliminates the routine part. If the pre-filter says "looks coherent overall, but three evidence claims have no citation" — the human knows where to start.

**Regression of your own comments.** Collect review notes: "third time I added the missing-citation comment", "another invented API field". After a few weeks you have a map of the agent's weaknesses. Some will go into the system prompt, some into `AGENTS.md`, some will live permanently on your checklist.

Review quality grows with process maturity. The first reviews are long. The tenth ones are fast, because you know where things usually break.

## Worth remembering

- Five evaluation dimensions: completeness, factual correctness, domain alignment, traceability, "pretty nonsense" risk.
- Each dimension catches a different class of error. Skipping any of them is a quality leak.
- A fifteen-point checklist fits in a fifteen-minute review.
- Five situations where you reject without discussion and send back. Sending back is cheap.
- Scaling: AI pre-filter + regression of your own comments into the system prompt and `AGENTS.md`.
